# 04 双模型竞速：聊天和意图分类并行

> 一个模型既要会聊天又要会精确地调工具，往往两头都不够好。一种生产里验证过的做法：两个模型并行跑，一个负责说话，一个负责判断要不要做事，运行时按决策矩阵合并结果。

## 学习目标

- 能画出双模型并行的时序，并说出运行时在什么时刻做合并决策
- 能写出决策矩阵的四种情况及各自的处理
- 能说出这个架构的三个主要代价

## 心智模型

```mermaid
flowchart LR
    U[用户一句话] --> C[聊天模型<br/>擅长人设和自然语言<br/>可能不支持或不擅长工具调用]
    U --> I[意图模型<br/>小、快、专门微调<br/>只输出：要调什么工具，或"只是聊天"]
    C --> R{运行时合并}
    I --> R
    R -->|只是聊天| S1[用聊天模型的回答]
    R -->|只有命令| S2[执行命令，取消聊天生成]
    R -->|命令 + 聊天| S3[执行命令，同时用聊天回答]
    R -->|意图模型超时| S4[退回只聊天]
```

## 要点

1. **动机是能力分工。** 人设强、语气自然的模型往往工具调用不稳；工具调用准的模型说话像客服。与其找一个都行的，不如两个各干各的。
2. **两个模型同时发请求，不串行。** 串行等于延迟相加。并行的话总延迟接近两者中慢的那个，通常是聊天模型，意图模型是小模型很快回来。
3. **决策矩阵是运行时的确定性代码，不是第三个模型。** 意图模型输出分四类：纯聊天、纯命令、命令加聊天、无法判断。每类对应的处理是写死的。
4. **"纯命令"时要取消聊天模型的生成。** 用户说"音量小一点"，正确的反应是音量变小，而不是模型说一段"好的我来帮你把音量调小"。取消要快，否则 TTS 已经开始播了。
5. **"命令加聊天"是最常见也最微妙的。** 用户说"太吵了，讲个故事吧"：既要调音量，又要开始讲故事。运行时先执行命令，再让聊天模型的回答继续。
6. **意图模型的输出仍然要过第 05 课的全部守卫。** 它是专门微调的，但一样会输出没注册的工具名和缺字段的参数。作者的项目里这两种错误都真实出现过，靠注册表和 schema 校验兜住，没有改提示词。
7. **聊天模型正文里的"伪工具调用"一律当文本。** 聊天模型看过太多工具调用格式的文本，偶尔会在回答里写出一段像函数调用的 JSON。运行时只认意图模型的结构化通道，这条规则救过场。
8. **代价一：成本翻倍。** 每轮两次模型调用。意图模型小，增量通常是 20%～40%，不是 100%。
9. **代价二：一致性。** 两个模型对同一句话的理解可能不同。聊天模型说"好的我来放歌"，意图模型判定"只是聊天"，于是没放歌。缓解手段是让聊天模型的 system prompt 里明确"你不负责执行动作，只负责回应"，并在合并时以意图模型为准。
10. **代价三：调试复杂度。** 一轮对话有两条模型轨迹加一次合并决策，没有 trace 根本看不清发生了什么。第 18 课的 trace 在这里是必需品。
11. **停止条件收回运行时。** 作者的项目早期让聊天模型"自然停下"，和竞速逻辑叠在一起后谁负责结束变得模糊。后来加了显式的退出工具由意图模型触发，运行时收到就静默终止，稳定多了。这是第 06 课要点的直接来源。
