# 26 系统设计与技术决策

> 好的 AI 系统设计不是堆组件，而是把目标、约束、证据、取舍和重新决策的条件写清楚。

<details class="case" markdown="1">
<summary>例子：团队在 RAG、微调和换大模型之间争论，却没有定义成功标准</summary>

如果没有任务集、延迟上限、预算和数据更新频率，三种方案都能讲出优点。真正需要先写的是：什么问题要改善、允许付出什么代价、多久验证一次。

!!! note "构造的例子"
    方案争论用于说明决策记录的必要性；真实选型应使用项目数据。

</details>

## 一份 ADR 至少回答六件事

1. 要解决的用户或业务问题是什么？
2. 成功指标和硬约束是什么？
3. 候选方案分别依赖哪些假设？
4. 选择方案的证据是什么？
5. 什么时候重新评估或退出？
6. 如何灰度、回滚和观测？

## 常见选择不是二选一

| 决策 | 先看什么 | 常见默认 |
|---|---|---|
| Workflow / Agent | 路径是否可枚举 | 能写死就先写死 |
| Prompt / RAG / 微调 | 知识是否变化、行为是否稳定 | 变化知识先用 RAG |
| 单体 / 平台 | 团队和租户边界 | 先保持边界少 |
| 自托管 / API | 流量、隐私、运维能力 | 先用 API 验证需求 |
| 大模型 / 小模型 | 任务质量和成本 | 用评测决定路由 |

“默认”不是结论。它只是成本最低、最容易验证的起点。

## 容量和退出条件要写在一起

容量估算至少列出日请求、峰值倍率、每轮 token、p95 延迟和并发资源。退出条件要能被观测，例如“连续两周成本超过预算且小模型无质量差异，就重新评估路由”。

## 怎么测

拿一项真实决策写成一页 ADR，再用以下问题复核：

- 另一个人能否根据记录复算结论；
- 每个关键假设是否有测量来源；
- 失败时是回滚、降级还是继续实验；
- 三个月后还能看懂当时为什么没有选另一个方案。
