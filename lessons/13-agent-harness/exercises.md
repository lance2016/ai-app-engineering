# 13 Agent Harness：把前八课装进一个真实系统｜练习

## 练习 1：这条规则该放哪一层

下面五条规则，各自应该落在权限声明、调用前 hook、调用后 hook，还是系统提示词里？

1. 改完任何 `.py` 文件后，跑一遍格式化工具
2. 不允许写 `migrations/` 目录下的任何文件
3. 回答里出现代码时，用中文注释
4. 每条 `run` 命令都自动加上超时上限
5. 删除文件前必须问一次用户

<details><summary>答案</summary>

1 调用后 hook。它是"动作发生之后必然要做的事"，模型不需要知道它存在。

2 调用前 hook（或者权限门里的一条路径规则）。注意它不适合写成工具的可逆性声明——可逆性是工具级的，这是参数级的判断，要看具体路径。

3 系统提示词。这是风格，不是纪律，做不到也不会造成损失。**提示词该管的就是这类事。**

4 调用前 hook 改参数。这也说明 `hooks.pre` 为什么要能改参数，而不只是能否决。

5 权限声明。`run` 里的 `rm` 是绕过声明的典型路径，所以正文的工具描述里写了「不要用 run 读写文件」——但描述挡不住有决心的模型，真正的兜底是命令前缀白名单。

第 3 条和其他四条的区别值得记住：**做不到会造成损失的规则，不能只写在提示词里。**

</details>

## 练习 2：让 edit_file 更难用错

正文的 `edit_file` 在匹配到多处时会报错。现在加一个参数 `expected_count: int = 1`，允许调用方明确声明"我知道有三处，三处都要改"。

验收：`expected_count` 和实际匹配数不一致时仍然报错，并且错误信息里要同时给出实际数量和原文里那几处各在第几行。

<details><summary>参考答案</summary>

关键不在参数本身，在错误信息。只说"期望 1 处，实际 3 处"，模型下一轮只能瞎猜；把三处的行号一起给出来，它可以直接选一处扩上下文，或者确认三处都该改。

这是第 05 课「错误回喂」在这一课的具体形态：**错误信息是给模型的下一条指令，不是给人的日志。** 判断一条错误信息写得好不好，标准就是"模型看完知不知道下一步做什么"。

顺带一提，加了这个参数之后要盯住一个退化：模型可能学会用 `expected_count=99` 来绕过唯一性检查。所以实际匹配数必须严格等于声明值，不能写成"至少"。

</details>

## 练习 3：审批疲劳的一次改造

某个 harness 上线后收到反馈：用户平均每分钟被问两次，三天后所有人都在无脑点同意。翻 trace 发现，八成的询问来自 `run` 工具，而这些命令里绝大多数是 `git status`、`ls`、`pytest` 这类只读命令。

给出一个改造方案，并说明它会带来什么新风险。

<details><summary>参考答案</summary>

方案：给 `run` 加一层命令前缀白名单，白名单里的命令降级成只读，不再询问。白名单放配置，不放代码。

新风险有三个，都要一起处理：

一是命令拼接。`git status && rm -rf .` 的前缀也是 `git status`。判断必须在解析后的命令上做，不能对整个字符串做前缀匹配。

二是白名单会长。每次有人抱怨就加一条，半年后它形同虚设。所以要给白名单加审计：谁加的、什么时候、因为什么。

三是 `pytest` 并不只读——它会执行仓库里的代码，那些代码可以做任何事。**「命令看起来只读」和「命令的效果只读」是两件事**，这条边界最终只能靠沙箱兜，不能靠白名单。

</details>

## 练习 4：压缩之后它忘了自己在干什么

一个长任务跑到第 120 轮触发压缩，压缩后模型开始重做第 30 轮已经做完的事，还把一个改好的文件又改了一遍。

不写代码，回答两个问题：这是哪一层的问题？如果只允许改一个地方，改哪里？

<details><summary>参考答案</summary>

不是模型的问题，是运行时的问题。待办状态被放在了对话历史里，而历史是会被压缩的东西——摘要保留了"聊过什么"，丢掉了"哪几步已经完成"。

只改一个地方的话，改状态的存放位置：把待办清单从对话历史里拿出来，变成运行时状态（第 07 课），每一轮原样重新拼进上下文，不参与压缩。这样压缩丢的只是叙述，不是事实。

值得注意的是另一个更贵的选择：把压缩阈值调高。它治标，而且推迟问题的代价是每一轮都更贵。**结构性问题不要用参数解决。**

</details>

## 练习 5：判断题，不写代码

一个团队说：「我们的 Agent 只在容器里跑，容器随时可以扔掉，所以不需要权限门，全开 auto 模式就行。」

这个论证哪里成立、哪里不成立？

<details><summary>参考答案</summary>

成立的部分：容器确实解决了「把宿主机搞坏」这一类风险，文件系统的破坏是可恢复的。

不成立的部分有三处，而且都不是沙箱能挡的：

一是容器里往往有凭据。环境变量里的 API key、挂进来的 git 凭据、云厂商的元数据服务，Agent 都能拿到，它们的作用范围在容器外面。

二是不可逆的动作大多在网络另一端。发邮件、提 PR、调支付接口、删远端分支，这些做了就是做了，容器扔掉也收不回来（原则 06）。

三是没有权限门就没有审批事件，也就没有「它到底做了什么」的记录。出了事只能靠读日志猜（原则 09）。

正确的说法是：**沙箱和权限门挡的是不同的东西。** 沙箱管「影响能扩散到多远」，权限门管「这个动作该不该发生、谁批的」。有了容器可以把权限门调松（比如工作目录内的写不再询问），但不能把它拆掉。

</details>
