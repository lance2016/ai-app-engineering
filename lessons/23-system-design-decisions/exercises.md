# 23 系统设计与技术决策｜练习

## 练习 1：把估算器接到真实假设上

用 `01_capacity_estimator.py` 估你手上（或想象中）一个 AI 产品的容量。把每个假设的来源写在注释里（日志、竞品、拍脑袋）。

验收：能说出三个最不确定的假设，以及各自误差一倍时对每日花费的影响。

<details><summary>提示</summary>

通常最不确定的是 `input_tokens_per_turn`（历史和检索结果的长度）和 `turns_per_user_per_day`。前者直接乘在成本上，这也是第 08 课上下文裁剪和 prompt cache 为什么是成本问题而不只是质量问题。

</details>

## 练习 2：给决策矩阵加一列"不做"

`03_decision_matrix.py` 的三个选项都是"做"。加第四个选项"继续手工评测，不引入平台"，给它打分。

验收：`flips()` 的输出里出现或不出现这个选项，你都能解释为什么。

<details><summary>答案</summary>

"不做"通常在"time to first value"和"3-year cost"上得高分，在"fit"上得低分。如果加进去之后它成了赢家，说明你还没证明平台的必要性；如果它稳定垫底，说明现状确实撑不住了。两种结果都是有用的信息，这就是为什么"不做"必须在选项里。

</details>

## 练习 3：给一个已有决定补 ADR

选你项目里一个已经做出但没有记录的技术决定，用 `02_adr.py` 的结构写出来，重点写 `exit_criteria`。

验收：至少两条退出条件是可观测的量（比率、次数、时长），不是"如果效果不好"。

<details><summary>提示</summary>

好的退出条件长这样："某指标连续两周低于 X"、"某类事故一个季度超过 N 次"、"某成本占比超过 Y%"。它们能从第 17、18 课的评测和 trace 里直接读出来。

</details>

## 练习 4：四类决策的快速判断

每题一句话给出默认选择和一个会让你改主意的条件：

1. 内部知识库问答，文档每周更新，需要引用：RAG 还是微调？
2. 报销审批流程，步骤固定，合规要求高：Workflow 还是 Agent？
3. 团队 3 人，第一个 AI 功能刚上线，第二个团队说想复用模型网关：现在平台化吗？
4. 需要 LLM trace 平台，数据不能出境：自建、买 SaaS 还是自托管开源？

<details><summary>参考答案</summary>

1. RAG。改主意的条件：需要改变模型的语气、格式或推理风格，而不是补知识。
2. Workflow，模型只放在需要理解自然语言的节点。改主意的条件：审批路径真的无法枚举，且允许探索。
3. 不。先让第二个团队直接 import 你的模块，等他们的需求稳定再抽象。改主意的条件：配额和隔离已经造成了事故。
4. 自托管开源。改主意的条件：团队没有运维能力，且供应商能提供境内部署。

</details>

## 练习 5：综合设计题

设计一个面向多个企业租户的"知识库 + 任务 Agent"平台，支持文档权限、MCP 工具、Skill、流式对话、人工确认、可追溯引用、模型故障切换和成本预算。写出下面六个部分，每部分半页以内。

1. 数据、租户、权限和删除边界
2. Workflow 与 Agent 的控制流
3. MCP Server 与 Skill 的版本和供应链
4. RAG、Memory、业务 API 的职责分工
5. Eval、trace、SLO、告警和回滚
6. 质量、延迟、成本、安全和交付周期的取舍

<details><summary>参考答案骨架</summary>

**1. 边界。** 租户 id 是每张表的第一列和每次检索的硬过滤，不靠应用层"记得加"。文档权限在索引时写入 chunk 元数据，检索时按用户可见集合过滤，而不是检索后再删。删除是先标记后物化，24 小时内完成，事件线程里引用被删文档的引用要能降级显示。长期记忆按租户和用户双重隔离，带来源，用户可查可删。

**2. 控制流。** 外层是确定性 Workflow：鉴权、路由、预算检查、审计。Agent 只在"需要理解自然语言并选择工具"的节点内运行，步数上限按场景配置。人工确认是 `request_human_input` 工具加第 07 课的暂停恢复，状态存在事件线程，不存进程内存。多 Agent 只在任务明确可拆时用，交接时只传摘要不传全部历史。

**3. 供应链。** MCP Server 像依赖一样管理：锁定版本、记录能力清单的哈希、每次升级跑回归。只读 Server 和有副作用的 Server 分开审批。Skill 是仓库里的文件，走代码评审和版本标签，运行时按需加载，加载记录进 trace。第三方 Skill 默认沙箱运行。

**4. 分工。** RAG 回答"文档里说了什么"，带引用；业务 API 回答"现在的事实是什么"，每次实时查，不缓存进上下文；Memory 只存跨会话的用户偏好和已确认的事实，不存业务数据。三者的结果在上下文里分区标注，模型知道每段话的性质。

**5. 质量运维。** 每个租户一份 Golden set，上线前 Recall@k 和任务成功率过门禁。OpenTelemetry 打 trace，GenAI 语义约定，接 Phoenix 或 Langfuse，租户 id 是必带属性。SLO 至少三条：首 token 延迟、任务成功率、错误引用率。模型故障切换是 adapter 层的策略，切换事件进 trace。回滚对象是提示词版本、Skill 版本、模型版本三者，每个独立可回滚。

**6. 取舍。** 质量优先的场景（法务、合规）用大模型加人工确认，接受延迟；效率优先的场景（内部问答）路由到小模型，接受偶尔转人工。成本靠 prompt cache、模型路由、上下文裁剪三个杠杆，用 `01` 的估算器算每个杠杆的收益。安全边界由代码执行，不靠提示词。交付分三期：单租户单体、多租户隔离、平台化，每期有退出条件。

用 `02_adr.py` 的格式把其中至少三个决定写成 ADR，这是 M6 的验收之一。

</details>
