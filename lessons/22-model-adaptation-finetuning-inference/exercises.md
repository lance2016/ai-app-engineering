# 22 模型适配、微调与推理服务｜练习

## 练习 1：给估算器加一个真实模型

去任意一个开源模型的 Hugging Face 页面找 `config.json`，读出 `num_hidden_layers`、`num_key_value_heads`、`hidden_size / num_attention_heads`（头维度）和参数量，套进正文的显存公式算一遍。

验收：能回答"这个模型 int4 权重加 4 路 16k 上下文的 KV cache，一张 24G 消费卡够不够"。

<details><summary>提示</summary>

`num_key_value_heads` 等于 `num_attention_heads` 就是 MHA，小于就是 GQA。头维度一般是 128。参数量在模型名里或 `README` 里。算出来的数字和推理引擎实际占用会差 10% 到 20%（激活值、碎片、引擎开销），做容量规划时留这个余量。

</details>

## 练习 2：KV cache 量化

`01` 假设 KV cache 是 fp16。给 `kv_cache_bytes` 加一个 `kv_bytes` 参数，算 int8 KV cache 的情况。然后回答：对哪一列的影响最大？

<details><summary>答案</summary>

传 `bytes_per_value=1.0`。影响最大的是"kv 8x32k"那一列，直接减半，因为它完全由 KV cache 构成；权重列不变。

这说明长上下文、高并发的服务，KV cache 量化比权重量化更值钱。vLLM 等引擎支持 fp8 KV cache 就是为这个场景。但 KV cache 精度下降对质量的影响要在自己的评测集上验，尤其是长文档问答。

</details>

## 练习 3：临界点的敏感性

用正文的成本公式回答：在默认假设下，GPU 小时价降到多少时，自建在 60% 利用率下开始比 API 便宜？吞吐提高到多少也能达到同样效果？

<details><summary>答案</summary>

自建每百万 token 成本 = 小时价 / (吞吐 × 3600 × 利用率) × 1e6。要低于 API 的 0.525，在吞吐 1500、利用率 60% 下，小时价要低于约 1.70 美元；或者小时价不变，吞吐要超过约 2200 token/s。

两个杠杆里吞吐更可控：换更好的批处理、量化、speculative decoding 都能提吞吐；GPU 价格你说了不算。但吞吐提升往往伴随延迟上升（批越大等待越久），第 20 课的 SLO 会限制你能开多大的批。

</details>

## 练习 4：判断该不该微调

三个场景，各用决策树走一遍，给出结论和理由：

1. 客服机器人经常把公司最新的退货政策说错
2. 抽取发票字段的任务，提示词已经写了两页，准确率卡在 91%，有 5000 张人工标注过的发票
3. 一个新上线的功能，产品经理还在每周改输出格式

<details><summary>参考答案</summary>

1. RAG。这是知识问题，政策会变，微调既不可靠也追不上更新。
2. 微调的典型场景：行为问题（抽取格式和判断）、提示已经到头、有足够标注数据、任务定义稳定。前提是先确认评测集能区分 91% 和 95%，否则微调完不知道有没有用。
3. 停在提示层。任务定义在变，微调的样本一周就过期。等格式稳定三个月再考虑。

</details>

## 练习 5：写一节选型结论

为一个假想的多租户知识库平台写"模型与推理选型"一节，不超过 300 字，要包含：候选模型、显存估算结果、预期流量下的成本比较、最终选择、假设和复核日期。

<details><summary>参考结构</summary>

- 候选：托管 API（两家）+ 自建 8B GQA 模型 int8
- 显存：8B int8 权重 7.5G，8 路 16k 上下文 KV 16G，一张 24G 卡勉强，一张 48G 卡稳妥
- 流量：预期每月 800M token，低于临界点 3476M，API 更便宜
- 结论：第一年用托管 API，adapter 保持协议兼容；月流量超过 2000M 或出现数据出境限制时重新评估
- 假设：价格表 2026-09-04；模型结构按候选模型 config.json；利用率按 60%
- 复核：每季度，或价格变动超过 30% 时

结论里最有价值的一句是"什么条件下重新评估"。选型不是一次性的。

</details>
