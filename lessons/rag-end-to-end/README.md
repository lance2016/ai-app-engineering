# 15 RAG 端到端

> RAG 的价值不是“给模型加一个搜索框”，而是让一次回答能追溯到外部证据，并能定位错在数据、检索还是生成。

<details class="case" markdown="1">
<summary>例子：答案引用了正确文档，但引用的段落没有回答问题</summary>

文档确实被检索到，模型也给出了引用。仔细看发现候选片段缺少上一段的限定条件，模型用相似主题补出了结论。只检查“有没有引用”不够，还要检查引用是否支持答案。

!!! note "构造的例子"
    文档和答案用于说明证据链；实际失败样本应来自自己的 golden set。

</details>

## 先把 RAG 拆成七步

```text
解析 → 切块 → 索引 → 检索 → 重排 → 生成 → 引用校验
```

每一步都有不同的证据。最终答错时，同时保存原文、块、top-k、重排结果和送进模型的上下文，就能排除大部分猜测。

| 步骤 | 主要问题 | 主要指标 |
|---|---|---|
| 解析 | 文档是否读全 | 解析覆盖率 |
| 切块 | 语义是否完整 | chunk 质量、长度分布 |
| 索引 | 是否可被找到 | 索引新鲜度、残留 |
| 检索 | 正确块是否进 top-k | Recall@k |
| 重排 | 正确块是否排前 | MRR / nDCG |
| 生成 | 是否只用证据 | 引用支持率 |
| 校验 | 引用是否真的支持 | citation precision |

## 混合检索不是自动变好

向量检索擅长同义表达，关键词检索擅长产品名、错误码和编号。组合它们时要记录每一路的候选和合并规则，否则无法知道收益来自哪一部分。

权限过滤要尽早做。把别的租户文档送进模型，再靠 Prompt 要求它不要使用，边界已经晚了。

## 引用校验要独立于生成

生成结果至少要包含引用的 chunk ID。运行时检查：引用存在、属于当前用户、版本有效，并且答案中的关键断言能在引用中找到支持。找不到支持时，应该降低置信度、继续检索或明确说证据不足。

## 怎么测

构造带正确片段和引用关系的问题集，分别测：

- `Recall@k`：正确证据是否进入候选；
- `citation precision`：引用是否真的支持答案；
- 按租户、文档类型和版本切片的权限与新鲜度；
- 删除和更新后的残留率。

不要只看最终答案准确率，它无法告诉你坏在第几步。
