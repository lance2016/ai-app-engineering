# 术语索引

> 每条一到两句，说清它是什么、和相邻概念的区别，以及在哪一课展开。术语写法沿用课程正文：中文有通行译法的用中文，直译更生硬的保留英文。英文术语按字母序，中文术语按拼音序。「展开」列是课号，P 开头是原则编号。

## 英文术语

| 术语 | 一句话 | 展开 |
|---|---|---|
| A2A | Agent 之间的通话协议，解决两个独立 Agent 怎么互相发现和委派任务；和 MCP 的区别是 MCP 连的是能力，A2A 连的是对等的 Agent | 12 |
| ADR | Architecture Decision Record，一份记录「决定了什么、备选是什么、假设是什么、什么条件下推翻」的短文档 | 25 |
| Agent | 目标 + 模型决策 + 工具 + 状态 + 循环 + 边界。模型只负责建议下一步，执行、预算、停止都归运行时 | 06, 07 |
| BM25 | 基于词频和文档长度的关键词打分算法，稀疏检索的事实标准；对精确匹配强，对同义改写弱 | 14 |
| Build vs Buy | 自建还是采购的决策。课程的做法是写出假设和退出条件，而不是比功能清单 | 25 |
| Chat Completions | OpenAI 2023 年定型的调用接口，`messages` 进、`choices` 出。国产模型和 vLLM、Ollama 都兼容它，所以是跨供应商的默认选择 | 00, 02 |
| checkpoint | Agent 在某一步的完整状态快照。课程里就是事件线程存盘，用于暂停、恢复和回放 | 07 |
| chunk | 文档切成的检索单元。大小决定召回粒度，带来源、版本、权限标签和内容哈希 | 04, 14, 16 |
| compaction | 把老对话压成摘要以腾出上下文窗口，同时完整日志另存、关键事实不交给摘要 | 08 |
| Context Engineering | 运行时每一轮怎么把指令、历史、检索结果、工具结果拼成一个窗口。和 Prompt Engineering 的区别是后者只管单次调用的指令写法 | 08 |
| ContextBuilder | 按固定顺序、在 token 预算内组装上下文的组件，能打印出发给模型的完整消息 | 08 |
| double texting | 上一轮还没跑完用户又发了一条。三种策略：reject、enqueue、interrupt，没有策略等于行为未定义 | 07 |
| Embedding | 把文本映射成定长向量，语义接近则夹角小；需要先归一化再算余弦 | 04 |
| Evaluator-Optimizer | 一个模型生成、另一个模型评审并给修改意见的循环，算 workflow 不算 Agent，因为控制流是写死的 | 09 |
| fake adapter | 按剧本回答的假模型，实现 ModelAdapter 协议。课程默认用它：无 key、确定、可注入失败 | 00 |
| fallback | 主路径失败后切到备用路径，比如主模型超时切备用模型。要有确定的兜底，不是无限重试 | 10, 20 |
| few-shot | 在 prompt 里放几个输入输出示例让模型照样子做，属于单次调用的指令技巧 | 03 |
| golden set | 带标签和期望结果的评测集，用确定性断言在一秒内跑完，是回归门禁的基线 | 18 |
| GQA | Grouped-Query Attention，多个 query 头共享一组 KV，直接减小 KV cache 显存，决定能不能服务长上下文 | 22 |
| handoff | 一个 Agent 把控制权交给另一个 Agent。课程里做成工具调用，由运行时切换活跃 Agent 并决定历史给多少 | 10 |
| Human-in-the-loop | 运行时在关键动作前暂停，等人确认或修改后再继续。课程里「问人」是一个工具调用 | 07 |
| JSON Schema | 描述数据形状的标准。课程里用 Pydantic 生成，同一份既约束模型输出又做参数校验 | 02, 05 |
| JSON-RPC | MCP 底层的请求响应消息格式，带 id、method、params 和统一的 error 结构 | 11 |
| kappa | Cohen's kappa，扣掉偶然一致后的一致率，用来校准 LLM judge 和人工标注的分歧 | 18 |
| KV cache | 推理时缓存每层的 key 和 value，避免每生成一个 token 都重算前文；是长上下文显存的主要开销 | 01, 22 |
| Little's law | 并发数 = 到达率 × 平均停留时间。从峰值 RPS 和平均时长推并发运行数，做容量估算 | 25 |
| LLM Judge | 用模型给模型输出打分。必须用人工标注校准，从分歧案例改 judge 的 prompt | 18 |
| LoRA | 只训练一组低秩增量矩阵的微调方法，显存和存储远小于全量微调 | 22 |
| MCP | Model Context Protocol，能力的接入协议：运行时启动时发现别的进程暴露的工具，按统一格式调用。不替代第 05 课的任何守卫 | 11 |
| Messages API | Claude 的调用接口。`system` 和 `max_tokens` 是顶层字段，`content` 是块列表，工具结果挂在 user 消息里 | 00, 02 |
| ModelAdapter | 课程里的模型接口协议，只有 complete 和 stream；fake、DeepSeek、DashScope、OpenAI 都在它后面 | 00, 02 |
| OpenTelemetry GenAI 语义约定 | trace 属性的标准命名，如 gen_ai.request.model、gen_ai.usage.input_tokens，让不同工具能读同一份 trace | 19 |
| Orchestrator-Workers | 一个模型拆任务并分派给多个 worker，再汇总。和 parallelization 的区别是子任务由模型动态决定 | 09 |
| OTLP | OpenTelemetry 的传输协议，课程把自己造的 tracer 按它的格式发给 Phoenix | 19 |
| Parallelization | 把可独立的子任务并行发给模型再合并，子任务在代码里写死 | 09 |
| pgvector | PostgreSQL 的向量扩展，一个库同时管业务数据和向量 | 04 |
| PII | 个人身份信息。出口要脱敏，记忆和日志里也不能明文留 | 21 |
| Planner / Executor | 先让模型出计划、再逐步执行的模式。计划一旦定下控制流就是确定的，所以算 workflow | 09 |
| Plugin | 宿主软件的扩展包，回答「怎么装进某个产品」，和 Skill 回答的「怎么教模型用」不是一层 | 12 |
| prefill / decode | 推理的两个阶段：一次性处理输入（算力密集）和逐 token 生成（显存带宽密集），延迟特征不同 | 22 |
| Prompt Chaining | 把任务拆成固定的几步，每步一次模型调用，上一步输出是下一步输入 | 09 |
| Prompt Engineering | 单次调用里指令怎么写：系统指令、few-shot、输出约束、版本化与测试 | 03 |
| racing | 两个模型并行处理同一输入，按规则取舍。一个超时时要有确定的兜底 | 10 |
| RAG | 检索增强生成：解析、切块、索引、检索、重排、生成、引用七步流水线，每步有自己独有的坏法 | 14 |
| Recall@k | 前 k 个检索结果里命中了多少应该命中的，是检索层的核心离线指标 | 14, 18 |
| Responses API | OpenAI 的新端点，`input` 进、`output` 条目出。独有的是服务端存对话历史（`previous_response_id`）和内置工具 | 00 |
| Routing | 先分类再分发到不同的处理路径，分类可以是模型也可以是规则 | 09 |
| RRF | Reciprocal Rank Fusion，按名次倒数融合多路检索结果，不需要归一化分数 | 14 |
| Runtime | 执行 Agent 循环的宿主：调工具、存状态、控预算、处理中断。模型不在其中 | 06, 07 |
| Skill | 一段教模型「怎么用一组工具完成一类任务」的可复用说明，SKILL.md 格式，三级渐进式加载 | 12 |
| SLO | 服务水平目标，比如 p95 延迟和成功率的承诺值；告警和故障演练围着它设计 | 20 |
| span | trace 里的一段操作：有名字、属性、父子关系、开始结束时间和状态；错误 span 要同时 set status 和 record exception | 19 |
| SSE | Server-Sent Events，服务端到客户端的单向流；课程里流式回答和事件流默认用它 | 02, 17 |
| stop_reason | 循环为什么停：finished、step_limit、token_budget、time_budget 等，必须有名字 | 06 |
| Structured Output | 用 JSON Schema 约束模型输出格式，解析失败要能回喂重试 | 02 |
| temperature / top-p | 采样参数：前者拉平或尖锐化概率分布，后者截断低概率尾部。temperature 为 0 也不等于正确 | 01 |
| Thread | 课程里的事件线程类型：append-only 事件列表，消息、状态、待处理调用都从它推导 | 07 |
| token | 模型看到的最小单位，不是字也不是词。中文通常比英文更贵 | 01 |
| Tool Calling | 模型输出结构化的调用意图，运行时校验、授权、执行、回喂。成功是三件事：选对、参数有效、真的做了 | 05 |
| Tool Registry | 注册表：按名字查工具，配合请求级白名单决定模型能看到和能调用什么 | 05 |
| ToolSpec | 工具对模型的描述：名字、何时使用的说明、参数 JSON Schema | 05 |
| trace | 一次请求跨模型、工具、检索的完整 span 树，带关联 id | 19 |
| Workflow | 步骤由代码预先编排、模型只在节点内工作的流程。五种模式：chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer | 09 |

## 中文术语

| 术语 | 一句话 | 展开 |
|---|---|---|
| 白名单 | 请求级允许使用的工具集合。要在「告诉模型有什么」时就生效，dispatch 时的检查是第二道防线 | 05, 21 |
| 版本（文档） | 每个 chunk 带源文档版本，防止引用过期内容；版本变了只重处理变化的部分 | 16 |
| 长期记忆 | 跨会话保留的用户偏好或经验，每条带来源和时间，用户可定向删除 | 15 |
| 成本临界点 | 托管 API 和自建 GPU 花费相等的调用量，超过它自建才可能划算 | 22 |
| 重排 | 检索之后用更贵的模型对候选重新排序，提高前几名的精度 | 14 |
| 多租户 | 多个客户共用一套服务。身份绑定在运行时而不是模型参数上，数据、配额、用量都按租户隔离 | 21 |
| 反馈闭环 | 用户反馈带原因码和切片进入评测集，产品改动能被数据验证 | 23 |
| 分层定位 | 失败按数据、检索、上下文、模型、工具、控制流六层排查，不统一归因给模型 | P07, 18 |
| 工具结果整形 | 把巨大的工具返回整成「概览 + 引用 + 按需取更多」再放进上下文 | 08 |
| 供应链风险 | 第三方 Skill 或 MCP server 被替换或篡改的风险，用来源校验和内容哈希钉死 | 12, 21 |
| 故障演练 | 主动注入下游超时、模型空输出等故障，验证熔断、fallback、告警是否按预期工作 | 20 |
| 幻觉 | 模型存的是「什么词常跟着什么词」而不是事实，所以会生成看起来对的错话。应用层靠检索和校验兜住，不靠祈祷 | 01 |
| 灰度与回滚 | 新版本先给一小部分流量，指标退化就切回旧版本 | 20 |
| 回归门禁 | 评测分数按切片和基线比，任何切片退化就阻止发布。总分会掩盖退化 | 18 |
| 会话记忆 | 当前会话的消息和工具结果，权威来源是事件线程，不需要单独的「记忆系统」 | 15 |
| 混合检索 | 关键词（BM25）和向量两路同时检索再融合，各补对方的弱点 | 14 |
| 渐进式加载 | 只让元数据常驻上下文，模型选中后再加载正文。Skill 的三级加载是它的典型形态 | 08, 12 |
| 结构化日志 | 一行一个 JSON，带关联 id，机器可查；比一行一句话有用 | 19 |
| 决策树（模型适配） | 质量问题该用提示、RAG 还是微调：先看缺的是能力、知识还是格式 | 22 |
| 可逆性分级 | 按动作能不能撤销分级，决定直接执行、给撤销窗口还是先确认 | 23 |
| 控制流 | 循环怎么走、什么时候停、失败走哪条路，全部由运行时的确定性代码持有 | 06, P02 |
| 来源（记忆） | 每条记忆指向产生它的事件。没有来源的记忆无法追溯，也无法定向删除 | 15 |
| 令牌桶限流 | 按固定速率发令牌，请求拿到令牌才能发出，防止撞穿下游配额 | 20 |
| 录制回放 | 把一次真实运行的事件线程存成 fixture，在 CI 里重放做断言 | 18 |
| 幂等键 | 从工具调用派生的唯一键，外部系统据此识别重放，让超时重试只产生一次副作用 | 05, P06 |
| 模型路由 | 按任务、成本或故障状态在多个模型之间选择，主模型故障时切备用 | 20 |
| 内容哈希 | 对 chunk 或 Skill 正文算哈希，用于增量更新判断变化和供应链校验 | 12, 16 |
| 跑偏检测 | 模型重复发出相同的工具调用时判定为循环，警告一次后升级给人 | 06 |
| 配额 | 每个租户或用户允许的用量上限，按请求计算成本后归因 | 20, 21 |
| 切片 | 评测集按标签分组，比如按意图、语言、难度。分切片看才能发现局部退化 | 18 |
| 权限标签 | 跟随 chunk 的访问控制标记，检索时按用户过滤，防止别人的内容进上下文 | 16, 21 |
| 确认门 | 有副作用的工具先问用户，拒绝也是一个正常的工具结果 | 05 |
| 人工基线 | 不用 AI 时人工完成的质量和成本，判断功能该不该上 AI 的参照 | 23 |
| 任务状态 | 走到哪一步、在等什么、剩多少预算。从事件线程推导，不单独存 | 07, P05 |
| 熔断器 | 下游连续失败后暂时停止调用，过一段时间再试探，防止抖动拖死整条链 | 20 |
| 容量估算 | 从峰值请求量和平均时长推并发数，再推 GPU 或配额需求 | 25 |
| 沙箱 | 代码执行类工具的隔离环境，限制文件、网络和时间 | 21 |
| 删除演练 | 删掉一个源文档后，证明索引、缓存、记忆里的所有派生数据都不存在了 | 16 |
| 上下文窗口 | 一次调用能放进的 token 上限，是每轮都在花的预算；历史增长让多轮成本近似平方增长 | 01, 08 |
| 事件流 | 循环每追加一条事件就推给客户端，客户端看到的和存下来的是同一份 | 07, 17 |
| 事件线程 | append-only 的事件列表，是状态的唯一事实来源；消息、状态、待处理调用都是它的推导 | 07, P05 |
| 数据生命周期 | 数据从进入到删除的保留、删除、审计方案 | 21 |
| 提示注入 | 用户输入或工具结果里夹带的指令被模型照做。分直接和间接两种，靠确定性守卫拦，不靠提示词 | 21, P11 |
| 停止条件 | 循环什么时候结束：模型直接回答、步数、token、时间、跑偏。全部由运行时持有并有名字 | 06 |
| 退避重试 | 失败后等一段随机化的递增时间再试，有单次超时和总次数上限；只对可重试的失败用 | 20 |
| 退出条件 | 一个决策在什么条件下应该被推翻，写在 ADR 里 | 25 |
| 系统提示 | 单次调用里给模型的角色和规则说明，要版本化并纳入评测 | 03 |
| 新鲜度 | 索引里的 chunk 是否落后于源文档，有陈旧巡检 | 16 |
| 业务状态 | 订单、审批、文件等事实，权威来源是业务数据库，用之前重新查，不信线程里的旧结果 | P05, 07 |
| 引用回链 | 回答里的每个引用指向具体 chunk id，可以校验是否真的来自检索结果 | 14 |
| 预算 | 步数、token、时间、金额的上限，每轮结算后检查，耗尽时报告是哪一种 | 06, 20 |
| 运行时 | 见 Runtime。课程里两个词混用，指同一个东西 | 06, 07 |
| 增量更新 | 文档改了一段只重新处理那一段，用内容哈希判断变化 | 16 |
